# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"A Forja" / "Disciplina Absoluta" — a mobile-first anti-procrastination / discipline app
(Portuguese UI). TanStack Start (SSR via Nitro) + React 19 + Vite + Tailwind v4 + Supabase,
also packaged as an Android app via Capacitor. Built on Lovable — see `AGENTS.md`: commits
pushed to `main` sync back into the Lovable editor, so keep `main` working and never rewrite
pushed history (no force-push / rebase / amend of pushed commits).

## Architecture — the big picture

### Data is local-first; the cloud is a single JSON blob per user

- **One Zustand store** (`src/lib/store.ts`, ~1800 lines) holds _all_ app data — tasks, sessions,
  XP, streaks, achievements, life goals, books/reading, finance transactions, shopping lists,
  assistant chat, discipline score. It is `persist`-ed to `localStorage` under the key
  **`kairos-store-v1`** (legacy name — do not change it or users lose data).
- **Cloud sync** (`src/lib/cloud-sync.ts`) snapshots the whole persisted store into **one JSONB row
  per user** in Supabase `public.user_data` (RLS-scoped to `auth.uid()`). Last-write-wins,
  debounced ~1.5s, offline-aware (queues and flushes on reconnect). On sign-in it hydrates the store
  from that row via a shallow `useStore.setState`. There is **no relational schema** for domain data
  — Postgres only has `profiles` + `user_data` (see `supabase/migrations/`).
- When you add a new persisted field to the store, also add its key to **`SYNC_KEYS`** in
  `cloud-sync.ts`, or it will silently not sync.

### The store + `src/lib/*.ts` are the domain layer; components are thin

Business rules live in `store.ts` and pure sibling modules, not in routes/components:

- `discipline.ts` — discipline points/penalties; `store.tickDay()` applies day-rollover of unfinished
  non-recurring tasks and back-dated discipline penalties.
- `store.taskAppearsOn()` / `todaysTasks()` — recurrence expansion (daily/weekly/weekdays/custom/…).
- `store.dayStats()`, `performance.ts`, `analytics.ts`, `insights.ts`, `achievements.ts`,
  `missions.ts`, `task-occurrences.ts` — stats, nudges, gamification, per-occurrence records.
- XP/level math and `calcXp` are in `store.ts`.

### Routing (TanStack Start file-based, `src/routes/`)

- `__root.tsx` — app shell: providers, `<BottomNav>`, `<AssistantFab>`, global alarm loop, native
  init, PWA setup, and the Supabase `onAuthStateChange` listener that attaches/detaches cloud sync.
- `_authenticated/route.tsx` — layout route with `ssr: false`, a `beforeLoad` auth guard that
  redirects to `/auth`, plus `pendingComponent` / `errorComponent` so a single screen crash doesn't
  blank the app.
- `src/routes/README.md` documents the file-name → URL conventions (bare `$param`, `_layout`, splat).
- Route files ship to the **client** bundle — never top-level `import` a `.server.ts` module; load it
  with `await import("@/integrations/supabase/client.server")` inside a server handler.

### Server routes & AI

- `src/routes/api/*.ts` (`assistant`, `tts`, `transcribe`, `book-search`) use
  `createFileRoute("/api/x")({ server: { handlers: { POST } } })` and proxy to
  `https://ai.gateway.lovable.dev` using `process.env.LOVABLE_API_KEY` (never exposed client-side).
  Each handler calls `guardApiRequest(request)` first (`src/lib/api-guard.ts`) — same-origin check
  + in-memory per-IP rate limit (20/min). Not full auth; a proper fix would attach the Supabase
  session token from the client (currently these `fetch` calls send none).
- The assistant (`/api/assistant`) streams the Lovable gateway's `/v1/responses` SSE API and returns
  a **strict JSON schema**: `{ reply, actions: [{ type, label, payload }] }`. `ACTION_TYPES` in that
  file is the allowed set. `src/lib/assistant-actions.ts` parses each action's JSON `payload` and
  applies it to the Zustand store (creating tasks, transactions, goals, shopping items, etc.).

### Auth

- Email/password + Google OAuth (`lovable.auth.signInWithOAuth` in `src/routes/auth.tsx`).
- Client access: the lazy-singleton `supabase` proxy from `src/integrations/supabase/client.ts`
  (session in `localStorage`).
- Server, user-scoped queries: `requireSupabaseAuth` middleware (`auth-middleware.ts`).
  Admin/service-role: `supabaseAdmin` from `client.server.ts`.
- The connected Supabase project **requires email confirmation** (`mailer_autoconfirm: false`) and
  has the pwned-password check enabled. For local testing, either confirm the user in the Supabase
  dashboard or disable "Confirm email" under Authentication → Providers → Email. `auth.tsx` maps all
  Supabase auth errors to PT-BR messages and has a "confirm your email" state with resend.
- `.env` is **gitignored** (only `.env.example` is committed). It holds `VITE_SUPABASE_*`
  (public) locally; the SSR/admin path also needs `SUPABASE_SERVICE_ROLE_KEY` / `LOVABLE_API_KEY`
  from the deploy environment.

### SSR error pipeline

`src/server.ts` wraps `@tanstack/react-start/server-entry` to catch h3-swallowed 500s and render
`src/lib/error-page.ts`. `src/start.ts` registers `attachSupabaseAuth` (function middleware) and an
error middleware. `src/lib/error-capture.ts` + `lovable-error-reporting.ts` forward client and
server errors to Lovable.

### Native / Android / PWA

- `src/lib/native.ts` is the only Capacitor bridge — everything is gated by `isNativeApp()`, so the
  web build is unaffected. `src/lib/notifications.ts` schedules native `LocalNotifications`; a
  separate JS alarm loop in `__root.tsx` covers the web.
- The Android WebView loads the **published URL** (`capacitor.config.ts` `server.url`), not bundled
  files, because the app needs the server routes and Supabase. Full details in `ANDROID.md`.
- PWA service worker is configured in `vite.config.ts` (VitePWA) and registered only through the
  guarded wrapper `src/lib/pwa.ts`.

## Product infrastructure

- **Analytics** — `src/lib/track.ts` is a decoupled event layer (no in-app dashboard). It
  **only sends** when `VITE_APP_ID` **and** `VITE_ANALYTICS_API_URL` are set (POST to
  `<API_URL>/events` via `sendBeacon`); otherwise it's a silent no-op. Standard events
  (`app_open`, `sign_up`, `login`, `onboarding_completed`, `feature_used`, `content_created`, …)
  are already wired in `__root.tsx`, `auth.tsx`, `_authenticated/index.tsx`, `tasks.new.tsx`,
  `focus.$taskId.tsx`, `plans.tsx`. Never pass PII — see `.claude/skills/analytics-event`.
- **Plans / monetization** — `src/lib/plans.ts` defines FREE/PRO/PREMIUM + `Feature` gates.
  `DEMO_MODE = true` → `hasFeature()` always allows, `getUserPlan()` returns `"premium"`, no
  billing anywhere. `/plans` route is the comparison UI. To enable real paid tiers later: set
  `DEMO_MODE = false` and back `getUserPlan()` with the real plan (e.g. from `user_data`).
- **`.claude/`** — `rules/` (code, security, git — permanent), `skills/` (`add-synced-field`,
  `analytics-event`), `agents/` (`reviewer`). Deep code/security review: use the built-in
  `/code-review` and `/security-review` skills.
- **Env** — `.env` is gitignored; only `.env.example` is committed. Local dev reads `.env`;
  deploy provides `SUPABASE_SERVICE_ROLE_KEY` / `LOVABLE_API_KEY` / `VITE_*` from its own env.

## Gotchas

- **`vite.config.ts` uses `@lovable.dev/vite-tanstack-config`**, which already bundles tanstackStart,
  viteReact, tailwind, tsConfigPaths, nitro, the `@` alias, `VITE_*` env injection, and dedupe. Do
  **not** re-add any of those or the app breaks with duplicate plugins. Extra config goes through
  that wrapper's `defineConfig({ tanstackStart, vite: {...} })`.
- Product was renamed Kairos → "Disciplina Absoluta" / "Forja"; the persist key and some internal
  names still say `kairos`.
- Many components call `useStore()` with no selector (re-render on any store change). Acceptable,
  but prefer `useStore((s) => …)` selectors in new code.
